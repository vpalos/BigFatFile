# BigFatFile (BFF) Local Database Indexing with LMDB

## Overview

This document describes using LMDB for local database indexing in a distributed filesystem. BFFS utilizes a two-table approach to efficiently manage and query filesystem nodes.

1. Metadata table: `[NodeID] -> { name, size, timestamps, ... } `
   - Stores detailed information about each node (file/folder) using `NodeID` as the key and node metadata as the value.
2. Indexing table: `[ParentID:Hash(NodeName)] -> NodeID `
   - Stores parent-child relationships using a composite key format such as `ParentID:NodeName` with `NodeID` as the value.
   - To handle large node names and avoid collisions, hash `NodeName` and use `ParentID:Hash(NodeName)` as keys in the index table.

## Tables

### Metadata Table

**Purpose**: Stores metadata for each node (file or folder) in the filesystem.

- **Keys**: `NodeID` (unique identifier for each node)
- **Values**: Node metadata object (e.g., name, size, type, timestamp)

**Key Size**: Default maximum of 4KB (configurable up to 64KB).

**Example**:

```
Key: 1234 (NodeID)
Value: { "name": "file.txt", "size": 1024, "type": "file", "timestamp": "2024-09-15T12:34:56Z" }
```

### Index Table

**Purpose**: Stores parent-child relationships and enables fast look-up of child nodes based on node names within a parent directory.

- **Keys**: `ParentID:Hash(NodeName)` (where `Hash(NodeName)` is a hash of the node's name to avoid collisions)
- **Values**: `NodeID` (identifier for the child node)

**Example**:

```
Key: 5678:3f6e1a2b (ParentID:Hash(NodeName))
Value: 1234 (Child NodeID)
```

### Handling Multiple Values per Key

- **Collisions**: When hash collisions occur, multiple `NodeID` values may be stored for a single key.
- **Multi-Value Mode**: LMDB supports storing multiple values per key. Although managing multiple values introduces some overhead, we consider this to be generally efficient and should not significantly impact performance, especially since collisions are rare.

### Prefix Scanning

- **Efficient Lookups**: The index table allows quick discovery of child nodes given a parent ID and node name.
- **Scanning**: Use key prefix scanning (e.g., `ParentID:`) to list all child nodes for a parent.

## Example Operations

### Inserting a Node

To insert a new node, add entries to both the metadata table and the index table.

**Metadata Table**:

```
Key: 1234
Value: { "name": "file.txt", "size": 1024, "type": "file", "timestamp": "2024-09-15T12:34:56Z" }
```

**Index Table**:

```
Key: 5678:3f6e1a2b
Value: 1234
```

### Querying Child Nodes

To query child nodes for a given parent, scan the index table for keys starting with `ParentID:`.

### Moving a Node

To move a node from one parent to another:

1. **Remove**: Delete the node from the old parent in the index table.
2. **Add**: Insert the node under the new parent in the index table.
3. **Update Metadata**: Update any relevant metadata if necessary.

## Hashing

- **Hashing Node Names**: Use a fast, non-cryptographic hash function to generate `Hash(NodeName)`;
  - xxHash variants `xxh3_64` or `xxh3_128` are recommended;
- **Collision Handling**: The LMDB multi-value support is enough to manage hash collisions.

## Solutions

- Key-value datastore: [LMDB](https://lmdb.readthedocs.io/en/release/) ([py-lmdb](https://github.com/jnwatson/py-lmdb/));
- Hashing functions: [xxHash](https://github.com/Cyan4973/xxHash) ([python-xxhash](https://github.com/ifduyue/python-xxhash));

## Conclusion

Using LMDB with a two-table approach allows efficient storage and retrieval of filesystem nodes. The metadata table holds detailed node information, while the index table facilitates quick lookups and management of parent-child relationships. The use of multi-value support in LMDB ensures that even with occasional hash collisions, performance remains optimal.
