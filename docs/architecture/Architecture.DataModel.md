# BigFatFile Architecture: Data model

The tables that describe a tenant's files: the tree, uploads in progress, content,
permissions, file versions, the change log and the audit log.

## 1. File tree

- The `nodes` table keeps a row for each file or folder:
    - tree hierarchy is enforced via the `parent_id` column (an adjacency list);
    - listing a folder is one index lookup;
    - moving a folder is one row update plus a check that the destination is not inside
      the moved folder;
    - paths are not stored; instead they're computed with a recursive CTE (a query that
      walks parent links) when needed.
- Key columns:
    - `id`: UUIDv7, generated by whoever creates the node, including offline clients;
    - `tenant_id`, `drive_id`, `parent_id`, `kind`, `name`, `name_key`, `version`,
      `manifest_id`, `size`, `deleted_at`.
- `name`:
    - stored in Unicode NFC (composed form);
        - macOS hands out decomposed names, and two spellings of one name end-up as two files;
        - this was actually a bug I had to fix in v1 (in prod, no less);
    - normalised by every client at pick time, but also...
    - normalised by every endpoint that stores a name (create, rename, move, upload, sends),
      with the function in Contracts;
    - the server never trusts the client to have done it.
- `name_key`:
    - the name casefolded and Unicode-normalised (NFC);
        - in order: NFC, then simple case folding, then NFC again;
        - the folding table is Unicode 17.0 `CaseFolding.txt`, statuses C and S,
          generated into Contracts and `@bigfatfile/client` by
          `sdk/unicode/generate-case-folding.mjs`, so no platform's own casing rules
          are involved;
        - simple folding maps one character to one character: `ẞ` becomes `ß`, but `ß`
          does not become `ss`, and the Turkish dotted `İ` stays as it is;
        - a name with an unpaired surrogate has no key and is refused;
    - sibling names are unique on `name_key`, because Windows and macOS are
      case-insensitive and clients must detect collisions offline.
- Limits:
    - 64 levels deep, 4,096 characters per full path.
- Deleting a node moves it under the drive's trash root; restoring it moves it back.
- Metrics:
    - each drive keeps a `used_bytes` counter, updated in the same transaction as the
      change, so quota checks never have to sum up a whole subtree.
- Optional (later) full path cache per node:
    - a nullable `path_cache` column;
    - filled lazily;
    - has to be cleared for a subtree when a folder moves.

## 2. Uploads

- A file enters the tree only when its upload completes; until then it is a row in
  `uploads`, not in `nodes`.
- The `uploads` table has one row per upload in progress, keyed by the node ID:
    - `node_id` (primary key), `tenant_id`;
    - for a new file: `parent_id`, `name`, `name_key`, `size`, everything the node row
      will need;
    - for a new version of an existing node: `base_version`, the version the client saw
      when it started (`If-Match`);
    - `kind`: `simple` (one stream) or `chunked`;
    - `received_bytes` for a simple upload; `manifest` (the target chunk list) for a
      chunked one;
    - `expires_at`.
- One upload per node at a time: `node_id` is the primary key, so a second start on the
  same node is refused unless it resumes the same upload (same `base_version`, same
  manifest or fingerprint).
- Names:
    - a unique index on `(tenant_id, parent_id, name_key)` in `uploads` stops two
      concurrent uploads of the same name;
    - against `nodes`, the check at start is best-effort (409 if taken) and the check at
      completion is the authoritative one, through the unique index on `nodes`; if the
      name was taken meanwhile, the SDK completes under the conflict-copy name.
- Completion is one transaction:
    - insert the node (new file) or update it (new version, `If-Match` on `base_version`, `version + 1`),
    - write the manifest,
    - append the change-log row,
    - delete the `uploads` row.
- An upload with no activity for 24 hours is removed by the sweep job;
    - a pending new file disappears with it;
    - the same 24h grace applies to chunks, so chunks aren't collected for uploads that may still complete.

## 3. Content

How the tree reaches the bytes:

```
nodes ──current──► manifests ──┬── manifest_chunks ──► chunks ──► warehouse: chunks/<hash>
  │                    ▲        └── object_id ───────► objects ─► warehouse: <key>
  └── node_versions ───┘
```

- `nodes` is the tree:
    - a file row points at its current content through `manifest_id`;
    - a folder doesn't have one (NULL);
    - a node knows nothing about chunks or objects, only which manifest is current.
- `node_versions` is the history:
    - one row per `(node_id, version)`, with the `manifest_id` of that version, the actor and the time;
    - `nodes.manifest_id` is a copy from the most recent version, to avoid any joins when listing;
    - retention (30 days, a year, legal hold) prunes rows here and nothing else.
- `manifests` is content, immutable (`Architecture.FileStorage.md`, section 1):
    - one row per file version (with bytes actually changed);
    - in theory two versions (even two files) could point to the same manifest ID;
    - columns: `chunking`, `size`, `hash` (nullable) and `object_id` (nullable);
    - a chunked manifest has no `object_id`; its chunks are rows in `manifest_chunks`;
    - a whole-object manifest (`chunking: "none"`) has an `object_id` and no rows in `manifest_chunks`;
    - a rename or move creates no new manifest (the new version reuses it);
    - two nodes may point at one manifest (a saved copy, a restore), which is why a
      manifest is referenced by ID and never edited (immutable).
- `manifest_chunks` is the ordered chunk list of a chunked manifest:
    - `(manifest_id, position, hash, size)`;
    - a table rather than JSON inside the manifest, because:
        - "is this hash in the node's manifest" on `GET /nodes/{id}/chunks/{hash}` is
          one indexed lookup;
        - the mark phase of garbage collection is one query over retained manifests;
        - offset-to-chunk mapping is a running sum over `size` in `position` order.
- `chunks` is the inventory of stored chunks:
    - `(tenant_id, warehouse_id, hash)`, `size`, `created_at`;
    - one row per distinct chunk per tenant, however many manifests reference it (deduplication);
    - its key in the warehouse is derived from the hash, so the row stores no key.
- `objects` is the inventory of stored whole objects:
    - `(tenant_id, warehouse_id, id)`, `size`, `hash` (nullable), `key`, `created_at`,
      `upload_id` while a multipart upload is open;
    - one row per object, referenced by `manifests.object_id`; shared by the versions
      and copies that did not change the content, never by two different uploads;
    - the key is stored because it may be anything, which is the one place that is true.
- The rules that follow:
    - reading a file: `nodes` → `manifests` → either `manifest_chunks` → `chunks` →
      storage, or `objects` → storage;
    - the `nodes` row is never read for bytes;
    - writing a version, in one transaction (section 2):
        - insert `manifests` (with its `manifest_chunks` or `objects` row),
        - insert `node_versions`,
        - update `nodes.manifest_id` and `version`,
        - append `changes`;
    - deleting a node moves it under the trash root;
        - its manifests, chunks and objects stay until retention prunes the `node_versions`
          rows and garbage collection finds the content unreferenced;
    - garbage collection marks every hash in `manifest_chunks` and every `object_id` in
      `manifests` reachable from retained `node_versions`, plus what an open `uploads` row pins;
        - it sweeps `chunks` and `objects` rows that are not marked and older than
          24 hours, deleting their storage (`nodes` is not touched);
    - `tenant_id` is on every one of these tables, so row-level security and the
      per-tenant mark-and-sweep work the same way for all of them.

## 4. Permissions

What a user may do with a node is decided by rules on folders, found by walking up the
tree. The policy (why folders and never files) is in `Architecture.Tenancy.md` (section 3);
this section is about how it works.

### Roles

- `viewer`: list, read metadata, download.
- `editor`: everything a viewer may, plus create, upload, rename, move, trash and
  restore.
- `owner`: everything an editor may, plus grant and revoke rules, delete permanently,
  change the drive's settings.
- The roles are ordered: a higher role includes the lower ones.

### Tables

- `permissions`: one row per rule:
    - `tenant_id`, `node_id`: the drive root or folder the rule is on; a rule on a
      file is refused;
    - `principal_kind`, `principal_id`: who it is for;
        - `user`: one member of the tenant;
        - `group`: every member of the group, through `group_members`;
        - `tenant`: every member of the tenant;
    - `role`;
    - `created_by`, `created_at`;
    - primary key `(tenant_id, node_id, principal_kind, principal_id)`: one rule per
      principal per node;
    - an index on `(tenant_id, principal_kind, principal_id)`, for "shared with me".
- Creating a drive inserts one rule: the creator is `owner` of the root. There is no
  other record of who owns a drive.
- There are no deny rules. A rule only ever grants.

### Groups

- `groups`: one row per group:
    - `tenant_id`, `id`, `name`, `name_key` (unique per tenant, folded like a node
      name);
    - `source`: `manual`, or `directory` for a group that `sso.groups` keeps in step
      with an identity provider; `external_id` holds the directory's own ID for those;
    - `created_at`.
- `group_members`: one row per membership:
    - `tenant_id`, `group_id`, `user_id`, `added_at`;
    - primary key `(tenant_id, group_id, user_id)`;
    - an index on `(tenant_id, user_id)`, which is how a request finds the user's
      groups;
    - a row may only name a member of the tenant; removing a member from the tenant
      removes their memberships.
- No nesting: a group holds users, never groups. The request's principals are then one
  indexed read, and a group cannot contain itself.
- A membership change appends a change-log row of type `groups` with no node, so a
  desktop client or Replica re-evaluates what its user may see; the rows of
  `permissions` do not change.
- Deleting a group deletes its `permissions` rows and its memberships in the same
  transaction.

### The check

- The principals of a request are: the user, the user's groups, and `tenant`.
- Walk from the node up to the drive root. The nearest node that has a rule for any of
  the request's principals decides; the role is the highest among that node's matching
  rules.
- No rule on the way up means no access, which the API answers as 404, the same as
  for a node that does not exist.
- This is one query: a recursive CTE over `nodes` for the ancestors, joined with
  `permissions` on the request's principals, ordered by depth, first row. Depth is at
  most 64 levels and usually under ten.
- Nearest wins, so a folder rule may give more or less than the drive rule above it:
  an `editor` of the drive can be `viewer` of one folder.

### What each operation checks

- Read a node, list a folder, download: `viewer` on the node (for a listing, checked
  once on the folder; every row inherits the folder's answer).
- Create, upload a new version, trash, restore: `editor` on the folder the node is in.
- Rename: `editor` on the node's folder.
- Move: `editor` on the source folder and on the destination folder.
- Grant, revoke, delete permanently, drive settings: `owner` on the node.
- A tenant administrator is `owner` of every drive of the tenant, without a rule; the
  audit log records such access as administrative.

### What a user sees

- "Shared with me" is the list of nodes with a rule for one of the user's principals,
  read through the index above. Those nodes are the roots of what the user can open.
- Listing a folder shows every row, because the check is on the folder and rules are
  never on files. The listing is the same for every viewer and can be cached as one.
- A permission change appends a change-log row of type `permissions` on the node, so
  desktop clients and the Replica refresh what they show.

### Outside the tenant

- A share link is a rule whose principal is the link: `share_links (tenant_id, token,
node_id, role, password_hash, expires_at, created_by)`, with `role` either `viewer`
  or, for a file request, `uploader` (may add files to that folder and nothing else).
  A request that presents a valid token acts with that one rule and no walk.
- A guest is a tenant member with the `guest` tenant role: they have access only
  through rules that name them, and may not create drives or see the member list.
- Nothing grants anonymous write; a file request is the only way in for an unknown
  uploader, and it writes into one folder.

## 5. File versioning

- Every node has an integer `version` that increases on each change;
- Each file version is stored as a manifest (see `Architecture.FileStorage.md`, section 1);
- Every write carries the version the client last saw (`If-Match`);
    - the Origin rejects the write if the version changed in the meantime;
    - this detects every conflict case:
        - two web users;
        - a desktop client against the Origin;
        - two clients through one Replica;
        - a Replica syncing against the Origin.

## 6. Change log

- Every mutation of the tree inserts a row into `changes` in the same transaction:
    - per-tenant sequence number;
    - change type (created, updated, renamed, moved, deleted);
    - node;
    - parent;
    - new version;
    - actor (user and client ID);
    - time.
- The sequence number comes from a counter row on the tenant:
    - incremented inside the transaction, so sequence order == commit order;
    - a plain database sequence would not guarantee that.
- Clients read it with `GET /changes?since=<seq>` (`Architecture.ClientSynchronization.md`).
- Retention is configurable (default 90 days):
    - a client with an older cursor does a full tree resync.

## 7. Audit log

- Separate from the change log;
- Stores:
    - who did what;
    - sign-ins;
    - share-link visits;
    - downloads and permission changes.
- Retention depends on the plan (on cloud version).
- Uses a partitioned table, so old partitions can be dropped cheaply.
